# Taxi-Lang Claude Instructions

This file contains instructions and conventions for the Taxi-Lang project when working with Claude.

## Documentation

Documentation for the project is located in the `docs2.0` directory. This is a Next.js-based website with the following key locations:

- `docs2.0/src/pages/docs/` - Core documentation pages
- `docs2.0/src/pages/changelog/` - Changelog files and release notes
- `docs2.0/src/pages/docs/other-api-specs/` - Documentation for integrations with other API specs like OpenAPI

When updating documentation, look for the corresponding Markdown/MDX file in these directories.

## Commit Conventions

The project uses conventional commits for version control. When making commits:

1. Use the conventional commits format: `type(scope): description`
   - Common types: `feat`, `fix`, `docs`, `chore`, `refactor`, `test`
   - Scope should describe the component being modified (e.g., `openapi`, `core`, `compiler`)

2. Write meaningful commit messages:
   - The first line should be a concise summary (under 72 characters)
   - Add a detailed description in the commit body, explaining the changes and their purpose

3. Example commit format:
   ```
   feat(openapi): improve operation kind detection based on HTTP methods
   
   Default operation kinds are now determined by HTTP method:
   - GET, HEAD, OPTIONS default to read operations
   - POST, PUT, PATCH, DELETE default to write operations
   
   The x-taxi-operation-kind extension is still supported as an override.
   This provides a better developer experience with less boilerplate while
   maintaining backward compatibility.
   ```

## Changelog Generation

The commit messages are automatically used to generate the project's changelog:

1. The commit body is automatically included in the changelog
2. Make sure commit messages are clear and user-focused, as they will appear in release notes
3. The changelog is generated into `docs2.0/src/pages/changelog/` and is arranged by:
   - `_versions/` - Raw files output by the changelog generator for each release
   - `releases/` - Aggregated changelog files per minor version (bundles all patches)
   - `next.md` files contain unreleased changes

4. The changelog is generated by running `npm run changelog` from the root of the docs2.0 project

## Testing Code Changes

After making code changes:

1. Run the appropriate Maven tests to verify your changes:
   ```bash
   ./mvnw test -pl <module-name>
   ```
   Example: `./mvnw test -pl swagger2taxi`

2. Make sure all tests pass before committing changes

## General Development Practices

1. Maintain backward compatibility when possible
2. Look at existing code patterns and follow the established style
3. Add appropriate tests for new functionality
4. Update documentation to reflect code changes
